# Using AI Responsibly in Capstones

This policy follows the program's core principle: **use AI as a thought partner, not a shortcut. Own every line in your project.**

---

## The one rule that matters

**You must be able to explain any line of code you commit or merge.**

If AI wrote it and you can't explain it, it isn't done yet — go understand it first. That's the whole policy. Everything below is just how it plays out.

We check this naturally, not with surveillance:
- In **daily standup**, you talk about what you built. You can't narrate code you don't understand.
- In **code review**, a teammate reads your PR. "Why did you do it this way?" is a normal question — and a fair one.

---

## Encouraged

- Explaining a concept or an error you don't understand
- A second set of eyes on a stubborn bug
- Reading documentation faster
- Talking through an approach *before* you build it

---

## Be honest about the heavy lifting

If you used an agentic tool to generate a **complex** part of your project, just tell us.

This is an **honor system**, and it is *not* about getting in trouble. It's so we can make sure you actually understand that piece before you lean on it in a demo — or an interview. Telling us early means we can help you learn it. Hiding it means you'll be the one stuck when someone asks how it works.

---

## Why we care — the internship reality

On the job, you will **read far more code than you write** — reviewing pull requests, learning an unfamiliar codebase, debugging someone else's work. The skill that makes you valuable isn't generating code; it's *understanding* it.

The capstone is where you build that muscle. Let AI accelerate your learning — not replace it.
